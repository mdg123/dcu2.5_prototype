## 0. 왜 고치는가 (사용자 지적)

> "일부러 문제를 틀려서 이전 학년이나 학기로 이동하는 것은 좋아, 그러다가 **출발선을 확인해서 맞았음.**
> 그러면 이제는 진단결과를 제공하고 학습경로가 추천해야 하는데 **갑자기 원래 진단한 학년-학기의 문제가 나옴.**
> **진단이 언제 끝나는거야**"

조사 결과 — **v3 엔진에는 "출발선을 찾았다 → 종료" 조건이 아예 없다.**
v2/CAT 의 `_finalizeDiagNodeOutcome` 에는 전환 감지 조기종료(`endReason='position_found'`)가 있으나,
v3 전 구간에 대응 코드가 **한 줄도 없다.** v3 는 전환을 `branchVerdicts[unit]='pass'` 로 알고 있으면서
**진행 띠 라벨로만** 쓰고 종료에 쓰지 않는다.

원 단원 복귀는 `[P1 본류복귀 2026-06-11]` 로 명시된 **의도된 설계**다. 그 설계가 결함이다.

## 1-A. 단원 판정 규칙 — 사용자 확정 (2026-08-07)

> 큐에서 꺼낸 단원 노드의 문항을 틀리면(정답률 기준 미달) **그 단원과 연결된 선수 단원들이 큐에 추가**되어 진단 대상이 된다.

### 표본 크기와 통과 기준 — **프리셋으로 일괄 결정** (아래 "프리셋 선택" 절이 정본)

> ⚠ **이 절은 프리셋 도입 이전에 작성됐다.** 아래 [진단 시작 시 프리셋 선택] 절이 **정본**이며,
> `4문항 / 3개` 는 **고정 규칙이 아니라 "빠르게" 프리셋 하나**다. **기본값은 표준(5문항 / 4개)**.
> 문항 수와 통과 개수는 **한 묶음**으로 세팅되고 사용자는 프리셋만 고른다.

```
단원 진단 = 그 단원에서 <프리셋 문항 수> 출제
  → <프리셋 통과 개수> 이상 정답 → 통과
  → 그 미만                      → 실패 → 그 단원의 선수 단원을 **다음 라운드** 큐에 추가
```

### 🔴 **목표 단원(본류)에도 똑같이 적용한다** (사용자 확정)

> "**5문제를 보면 다 봐야지 틀렸다고 중단하지 말라고 말했는데**"

**모든 단원이 같은 규칙이다. 예외 없다.**
- 학생이 처음 고른 목표 단원도 **프리셋 문항 수만큼 전부 출제**한다.
- **1문제 틀렸다고 즉시 하향하지 않는다.** 표본을 다 본 뒤 `needPass` 미만일 때만 하향한다.
- 표준(5/4)이면 목표 단원도 **5문제를 다 풀고**, 4개 미만이면 그때 선수로 내려간다.

⚠ **PM 이 "본류는 한 번 틀리면 즉시 하향" 이라고 잘못 지시했다.** 그것은 "차시당 1문제"를 확정하던 시점의
지시였고, 이후 **"조기 확정 제거 = 고른 수만큼 항상 출제"** 가 확정되면서 무효가 됐는데 거두지 않았다.
→ **화면이 "5문제 볼게요" 라고 하면 목표 단원에서도 5문제가 나와야 한다.** 안 그러면 화면이 거짓말이 된다.
→ 또한 "5문제 중 1개 오답"은 **통과**인데 목표 단원만 1개 오답으로 탈락시키면 **기준이 두 개**가 된다.

아래 표는 **"빠르게" 프리셋을 정할 때의 근거**로 읽을 것(왜 4문항이면 3개인가).

**왜 전 문항이 아니라 표본인가** — 실측: 문항 보유 단원 145개의 **단원당 문항 수는 중앙값 64 · 평균 69 · 최대 295**.
단원 하나를 다 풀면 평균 69문항이고 갈래가 3개면 200문항을 넘는다. 사용자가 지적한 *"진단이 언제 끝나는거야"* 가 그대로 재현된다.

**왜 4문항 / 3개인가** (4지선다 기준 찍기 통과 확률)

| 표본 | 통과 기준 | 실질 비율 | 찍기 통과 확률 |
|---|---|---|---|
| **4문항** | **3개** | **75%** | **5.1%** |
| 5문항 | 3개 | 60% | 10.4% |
| 4문항 | 2개 | 50% | 26.2% (기각 — 너무 헐렁) |

- **4문항 3개가 5문항 3개보다 찍기에 강하다**(5.1% vs 10.4%). 5문항은 "3개만 맞으면 되니까" 여유가 생겨 우연 통과가 두 배다.
- 갈래 3개면 **12문항**으로 끝난다.
- 엄격한 쪽(75%)이 안전하다 — 실패 판정이 조금 더 나와 **출발선이 낮게** 잡힌다. 낮으면 아는 걸 조금 더 볼 뿐이지만 **높으면 또 막힌다**(§2 와 같은 논리).

⚠ 사용자가 처음 말한 기준은 "정답률 60% 이하면 실패" 였다. **표본이 4문항이면 60%는 2.4개라 정수로 안 떨어지므로 실질 기준이 75% 가 된다** — 이 점을 고지하고 확정받았다.

**문항이 4개 미만인 단원**: 있는 만큼 출제하고 **과반** 으로 판정한다.

### 진단 시작 시 프리셋 선택 — 사용자 확정 (2026-08-07)

> "본 서비스를 **3단계 프리셋을 보여주고 선택**하도록 하고, **진단은 사용자가 스스로 하는 자기주도형**임.
> AI 맞춤학습의 사용자는 **교사·학생·학부모 누구라도** 사용 가능함."

**성격 규정이 중요하다** — 진단은 **평가가 아니라 본인이 쓰는 도구**다.
따라서 "학생이 기준을 낮춰 통과를 쉽게 만든다"는 남용 우려는 적용되지 않는다(자기 진단이므로 손해도 본인 몫).
반 평균·타인 비교도 목적이 아니다.

#### 프리셋 3단계 — **문항 수만 고르고, 통과 기준(정답률)은 고정**

| 프리셋 | 표본 | 통과 | 안내 |
|---|---|---|---|
| **빠르게** | 4문항 | 3개 (75%) | "짧게 확인할게요" |
| **표준** ⭐ | 5문항 | 4개 (80%) | 기본 선택 |
| **꼼꼼히** | 차시마다 1문항씩 **전부** | 80% | "시간이 걸려요" |

**왜 정답률을 열지 않는가** — 정답 개수는 정수라 **선택지가 서로 겹친다.** 실측 표:

| 문항 | 60% | 70% | 80% | 90% | 100% |
|---|---|---|---|---|---|
| 4문항 | 3개(75%) | 3개(75%) | 4개(100%) | 4개(100%) | 4개(100%) |
| 5문항 | 3개(60%) | 4개(80%) | 4개(80%) | 5개(100%) | 5개(100%) |
| 6문항 | 4개(67%) | 5개(83%) | 5개(83%) | 6개(100%) | 6개(100%) |

**4문항에서는 5개 선택지가 실제로 두 가지뿐이다.** 60%와 70%가 완전히 같고 80·90·100%도 같다.
→ 사용자가 고른 값과 실제 동작이 다른 화면이 된다(이 프로젝트가 반복해 잡아온 결함 부류).
그래서 **퍼센트를 고르게 하지 않고**, 화면에는 **"5문항 중 4개 정답"** 처럼 **실제 판정을 그대로** 쓴다.

#### 구현 요건
- 선택은 **진단 시작 화면**에서. 기본값 **표준**.
- 선택값을 세션에 저장(`difficulty_path` JSON 의 `sampleCap`/`needPass` 로 이미 자리가 있다 — `branchSample.sampleCap`).
- **"꼼꼼히"는 `cap = 그 단원의 차시 수`** 로 두되, 단원당 차시가 최대 몇 개인지 확인해 상한을 건다(문항 폭주 방지).
- 결과 화면에 **어떤 프리셋으로 진단했는지 표시** — 나중에 결과를 다시 볼 때 기준을 알 수 있어야 한다.
- 재개(`/v3/active`) 시 **처음 고른 프리셋을 유지**한다. 중간에 바뀌면 판정이 섞인다.

#### ⚠ 별건 확인 필요 — 비학생 진단 결과의 분리
교사·학부모도 진단을 한다. **실측: 교사 진단 세션 4건 · `user_node_status` 교사 행 3건이 이미 있다.**
2026-08-06 에 정본화한 학생 모집단 42곳은 대부분 `u.role='student'` 를 보지만 **진단·학습경로 계열은 그 42곳에 없었다.**
→ 교사·학부모의 진단 결과가 **학생 성취·LRS 통계에 섞이지 않는지** 별도 확인이 필요하다.

### 통과했을 때의 처리 — 사용자 확정 (2026-08-07)

| 항목 | 규칙 |
|---|---|
| 학습경로 | **포함하지 않는다** — 아는 단원이므로 |
| 그 단원의 선수 | **큐에 넣지 않는다** — 아는 것의 밑은 안다고 본다 |
| **이미 큐에 들어 있는 단원** | **전부 진단한다** ← 핵심 |

세 번째가 핵심이다. 구구단을 통과했다고 **자릿값을 안다는 뜻이 아니므로**, 이미 큐에 들어온 갈래는 끝까지 확인해야 출발선이 정확해진다(§2 와 같은 논리).

**따라서 학습경로에는 "실패한 단원"만 들어간다.**

```
두 자리 곱셈 실패
  → 큐: 구구단 · 자릿값 · 받아올림
       구구단   ○ → 경로 제외 · 아래로 안 내려감
       자릿값   × → 경로 포함 · 그 선수를 다음 라운드에 적립
       받아올림 ○ → 경로 제외 · 아래로 안 내려감
  → 큐 소진 → 종료
  → 출발선 = 자릿값 (실패한 것 중 가장 근본)
  → 경로: 자릿값 → 두 자리 곱셈
```

⚠ **통과해도 틀린 문항은 있다** — 통과 기준이 전부 정답은 아니므로(예: 4문항 중 3개) 틀린 문항이 남는다.
그 단원은 **학습경로에 넣지 않되, 틀린 문항은 오답노트에 남긴다**(현재도 진단 오답은 `_registerDiagnosisWrongNote` 로 자동 등록된다). 경로로는 안 가도 복습 경로는 유지된다.

### "연결된 단원" 의 방향과 시점
- **선수(prerequisite, 아래쪽 = 먼저 배워야 하는 것)** 만. 후속(위쪽)은 아니다.
- 실패한 단원의 선수는 **현재 라운드가 아니라 다음 라운드**(`nextRoundQueue`)에 적립한다.
  같은 깊이를 다 확인하고 내려가야 BFS 가 성립한다(§2·§6).

### 표본을 **무엇에서** 뽑는가 — 문항이 아니라 **차시(개념)**

현재 구현이 이미 그렇게 하고 있고, 이 방식을 유지한다.

```
단원 안의 차시를 여러 개 뽑아 → 차시마다 문항 1개씩 출제 → 통과한 차시 수로 판정
```

즉 **"N문항" = "차시 N개 × 문항 1개"**(N = 프리셋 문항 수)이지 랜덤 N문항이 아니다.
한 차시에서 여러 문항을 몰아 내면 그 차시만 알아도 통과하지만, 차시를 여러 개 훑으면 **단원의 여러 능력을 고루 확인**한다. 단원당 차시가 보통 5개라 표준(5)이면 거의 전부를 건드린다.

### 차시 선택 기준 — **고르게 흩어서** (사용자 확정 2026-08-07)

**결함(현재)**: `conceptOrder` **순서대로** 뽑는다. 차시 5개에서 4개를 뽑으면 **항상 앞의 4개**라 마지막 차시가 진단 사각지대가 된다.
→ "앞부분은 아는데 뒷부분을 모르는 학생"을 통과시켜 **출발선을 너무 높게** 잡는다.

**정본**: 단원의 차시 목록에서 **균등 간격**으로 `cap` 개를 고른다(양 끝 포함).
```
idx_i = round( i * (N-1) / (cap-1) ),  i = 0 … cap-1
예) N=5, cap=4 → 0, 1, 3, 4     (= 1·2·4·5번 차시)
    N=8, cap=4 → 0, 2, 5, 7
```
- `N <= cap` 이면 **전부** 사용.
- **진입 개념**(큐에서 꺼내 이 갈래로 들어온 개념)은 반드시 표본에 포함한다. 이미 seq[0] 이므로, 나머지 `cap-1` 개를 위 규칙으로 고른다.
- **문항이 없는 차시**(`skippedConcepts` 대상)는 건너뛰고 **다음 후보로 보충**한다. 보충해도 모자라면 있는 만큼으로 판정(§ 문항 4개 미만 규칙).

### ⚠ 묻는 **순서** — 조기 확정과 충돌하지 않게

조기 확정(`needPass` 도달 즉시 나머지 생략)이 있으므로, 균등하게 **뽑기만** 하고 순서대로 물으면
생략되는 것이 **대개 마지막 차시**라 사각지대가 되살아난다.

**정본**: 뽑은 표본을 **앞뒤로 번갈아** 묻는다.
```
뽑기(cap=4 예시) : 1 · 2 · 4 · 5
묻는 순서        : 진입 → 5 → 2 → 4      ← 마지막 차시를 두 번째로
```
이러면 **조기 확정으로 일찍 끝나도 단원의 앞·뒤가 모두 확인**된다. 속도를 살리면서 사각지대를 없앤다.

### 현재 코드와의 차이
- `_v3SampleVerdict` 의 `cap`·`needPass` 가 **하드코딩(현행 `cap=3 → needPass=2`)** → **프리셋 값에서 주입**
  (빠르게 4/3 · **표준 5/4 기본** · 꼼꼼히 차시 전부). `branchSample.sampleCap` 에 이미 자리가 있다.
- 표본 구성부(`branchSample` 생성, `sampleQueue: seq.slice(1)`)가 **순서대로 자르는 것 → 균등 간격 + 앞뒤 교차 순서**
- `needFail = cap - needPass + 1` 공식은 **그대로 두면 프리셋마다 알맞게 따라온다**
  (4/3 → needFail 2 "2개 틀리면 즉시 실패" · 5/4 → needFail 2 "2개 틀리면 즉시 실패")

## 1-B. 더 내려가기 전 **동의 확인** — 사용자 확정 (2026-08-07)

> "진단 단원을 통과하지 못하는 경우에는 출발선 확인을 위해 **추가 진단 단원(~개)를 추가**하려고 합니다.
> **시간이 보다 소요될 예정입니다** 라는 멘트와 함께 **동의 여부를 물어봐야** 지 — [추가 진단 동의] / [진단 종료하기]"

### 언제 묻는가 — **단원이 실패할 때마다** (사용자 확정)

> "**단원 실패할때마다 물어야지. 그래야 사용자가 알지**"

한 단원이 실패해 **그 단원의 선수가 큐에 추가되는 순간마다** 묻는다.
본류 실패 후 첫 하향도, 갈래 단원이 실패할 때도 각각 묻는다.

※ PM 이 처음 "라운드당 한 번"으로 제안했으나 **사용자가 뒤집었다.** 근거:
진단은 **자기주도**이므로 학생이 *"이 단원도 못 했구나 → 그래서 더 봐야 하는구나"* 를
**그때그때 알아야** 하고, **그만둘 기회도 매번** 있어야 한다. 성가심보다 **알 권리**가 우선.

**메시지의 개수는 "이번에 추가되는 단원 수"** 다(전체 예상이 아니라 이 단원의 선수 수).
매번 그 시점의 확정값을 쓴다.

### 무엇을 보여주는가 — **정확한 수를 예고한다**
조기 확정을 없앴으므로(§1-A) **추가 문항 수가 정확히 계산된다**: `추가 단원 수 × 프리셋 문항 수`.
추정치가 아니라 확정값이므로 **그대로 알려준다.**

```
┌──────────────────────────────────────────────┐
│  이 단원은 아직 어려운 것 같아요               │
│                                              │
│  더 아래 단원 3개를 확인하면                   │
│  어디서부터 공부할지 더 정확히 찾을 수 있어요. │
│  문제 15개가 더 나와요.                        │
│                                              │
│  [ 추가 진단에 넣기 ]      [ 넣지 않기 ]       │
└──────────────────────────────────────────────┘
```
- 문구는 초등학생이 이해할 평이한 한국어. 라벨은 명사형 유지.
- **주요 CTA 1개만 강조**(`추가 진단에 넣기`), `넣지 않기` 는 톤 다운.

### 선택에 따른 동작 — **최종 확정** (2026-08-07)

> "**계속하기 말고 [추가 진단에 넣기] / [넣지 않기] 이렇게 하고,
> 넣지 않으면 현재 큐에 들어간 진단 단원의 문제만 나오는 걸로**"

| 선택 | 동작 |
|---|---|
| **추가 진단에 넣기** | 그 단원의 선수를 `nextRoundQueue` 에 적립(기존 흐름) |
| **넣지 않기** | **적립하지 않는다.** 진단은 계속되고 **현재 큐에 이미 들어간 단원의 문제만** 나온다 |

🔴 **"넣지 않기"는 진단 종료가 아니다.** 그 단원 아래로 **더 안 파는 것**뿐이다.
→ 현재 큐의 남은 단원(다른 능력)은 **그대로 진행**되므로 §2("남은 갈래는 다 본다")가 깨지지 않는다.
→ 모든 단원에서 "넣지 않기"를 고르면 큐가 자연히 소진돼 **정상 종료**(§4-1)로 이어진다. 짧은 진단이 된다.

**진단을 아예 끝내는 것은 §5 중단 확인 모달**(결과 보기 / 나중에 이어서)이 담당한다. 두 모달의 역할을 섞지 말 것.

### ⚠ 알려진 트레이드오프 (사용자 인지하에 확정)
"넣지 않기"를 고르면 그 단원 **아래는 확인되지 않으므로 출발선이 실제보다 높게 잡힐 수 있다.**
PM 이 이 점을 들어 선택지 제거를 제안했으나 **사용자가 2지선다를 확정**했다 — 진단은 **자기주도**이고
학생이 자기 시간을 통제할 수 있어야 한다는 판단이다. **다시 제안하지 말 것.**

### 기존 모달과의 관계
§5 의 **중단 확인 모달**(학생이 스스로 그만두려 할 때: 결과 보기 / 나중에 이어서)과 **목적이 다르다.**
- §5 = 학생이 **먼저** 그만두려 함 → 이어하기 선택지 있음
- §1-B = 시스템이 **더 물어봐도 되는지** 허락을 구함 → 이어하기 없음(지금 결정)

**모달 컴포넌트는 같은 것을 재사용**하되(§5-3), 문구·버튼만 다르게 한다. 새 컴포넌트 금지.

### 회귀
- **단원이 실패할 때마다** 뜬다(라운드당 1회로 묶지 않음)
- 통과한 단원에서는 **뜨지 않는다**
- **예고한 단원 수·문항 수 == "넣기" 후 실제 추가·출제 수** ← 어긋나면 화면이 거짓말
- 🔴 **"넣지 않기"를 눌러도 진단이 끝나지 않고 현재 큐의 남은 단원이 이어진다** ← 구현 시 가장 헷갈리는 지점. 반드시 박을 것
- **"넣지 않기"를 누르면 그 단원의 선수가 큐에 안 들어간다**(적립 0건)
- 모든 단원에서 "넣지 않기" → 큐 소진으로 **정상 종료**

## 2. 왜 "남은 갈래는 다 본다" 인가 — 설계 근거

큐에 함께 들어가는 선수 단원들은 **같은 것의 쉬운 버전이 아니라, 서로 다른 능력**이다.

> 두 자리 곱셈을 못 풀면 → 구구단 · 자릿값 · 받아올림이 함께 큐에 들어간다.
> **구구단을 맞혔다고 자릿값을 안다는 뜻이 아니다.**

따라서 **첫 통과에서 즉시 종료하면 출발선을 너무 높게 잡아** 학생이 곧 다시 막힌다.
같은 라운드의 갈래는 전부 확인한다. 단, 갈래마다 **표본**(프리셋 문항 수)으로 판정하고 **조기 확정**이 있으므로
갈래 3개여도 실제 문항은 **표준 기준 12~15개 안쪽**이다. (표본 로직은 이미 구현돼 있다 — `_v3SampleVerdict`)

## 3. 출발선 판정 기준 — **바뀐다**

| | 기준 |
|---|---|
| ❌ 잘못된 기준 | 통과한 것 중 **가장 높은** 단원 |
| ✅ 정본 | **실패한 것 중 근본도가 가장 낮은(=가장 쉬운) 단원** |

구구단 ○ / 자릿값 × / 받아올림 ○ 이면 **출발선은 자릿값**이다.
잘하는 것이 아니라 **못 하는 것 중 제일 근본**에서 시작해야 한다.

※ `getDiagnosisResultV3` 의 `recommendedStartNode` 가 이미 "가장 근본 미통과 개념"을 고르므로
   **이 기준은 기존 구현과 일치한다.** 새로 만들 필요 없이 그 값을 그대로 쓴다.

## 4. 종료 조건 (신설·수정)

### 4-1. 정상 종료 — 라운드 큐 소진
`_v3BranchSamplePass` 의 **"큐 소진 → 본류 복귀"** 지점에서,
**후퇴가 한 번이라도 있었다면**(`downCount > 0`) 본류로 복귀하지 않고 **종료**한다.

- `finished = true` · `sessionComplete = true` · `endReason = 'position_found'`
- `attemptStage = 'finished'` · `nextQuestion = null`
- 세션 `status = 'completed'`
- **`_v3RestoreOriginUnit` 호출 금지** (이게 사용자가 본 "원래 문제 재출제"의 원인)
- ⚠ `downCount === 0`(후퇴 없이 본류만 푼 경우)은 **기존 흐름 유지** — 하위호환 및 정상 완주 경로 보호

### 4-2. 바닥 도달 — 하향 자원 고갈
`branch:{type:'down', prereqConcept:null}` 은 **의미상 종료인데 지금 종료 플래그가 없다.**
`finished/sessionComplete` 를 세팅하고 `endReason='floor_reached'` 로 종료한다.
(현재는 모달만 띄우고 사용자가 안 누르면 세션이 `in_progress` 로 영구 잔존 — 미종료 세션 생성 경로)

### 4-3. 죽은 브레이크 되살리기
```js
// 현재: 본문이 빈 if 문 (죽은 코드)
if (!resp.finished && (st.diagnosedConcepts||0) >= DIAG_V3_CONCEPT_CAP && !resp.nextQuestion) { }
```
`DIAG_V3_CONCEPT_CAP = 30` 이 **한 번도 적용된 적 없다.**
→ **강제 종료가 아니라 §5 의 중단 확인 모달을 띄우는 트리거**로 연결한다.

### 4-4. 라운드 깊이 상한 무력화 수정
`_v3DownTo` 가 본류 재진입마다 `st.prereqRound = 1` 로 리셋해
`DIAG_V3_DOWN_DEPTH_CAP = 8` 이 사실상 작동하지 않는다. 리셋 대신 보존한다.
※ 4-1 이 들어가면 이 경로를 거의 타지 않으므로 **우선순위 낮음**.

### 5-2. 무엇을 묻는가 — 2지선다

```
┌────────────────────────────────────────┐
│  여기까지 확인한 걸로 마칠까요?           │
│                                        │
│  지금까지 푼 것만으로도 어디서부터        │
```

| 선택 | 동작 |
|---|---|
| **결과 보기** | 세션 `completed` + 결과 화면 + **실패 단원 학습경로** 즉시 제공 |
| **나중에 이어서 하기** | 세션 `in_progress` 유지 + **진짜 재개 가능**해야 함(§7) |

## 6. 큐 정렬 방향 — 사용자 확정 ⑤

### 현재 (오름차순 = 낮은 학년 먼저) — 뒤집어야 함
```js
cand.sort((a, b) => (_gradeAbsOf(a) - _gradeAbsOf(b)) || (_sortOrderOf(a) - _sortOrderOf(b)));
st.prereqQueue.sort((a, b) => (_gradeAbsOf(a) - _gradeAbsOf(b)) || ...);
```

`_gradeAbs` 는 **학년·학기를 한 축으로 합친 값**이다(초1-1=2 … 초6-2=13, 중1-1=14, 고3-2=25).
따라서 **비교 한 번으로 "1순위 학년, 2순위 학기"가 동시에 해결된다.** 별도 학기 비교 불필요.

### 바꿀 형태
```js
cand.sort((a, b) => (_gradeAbsOf(b) - _gradeAbsOf(a)) || (_sortOrderOf(b) - _sortOrderOf(a)));
```

### 절단은 손대지 않는다 — 정렬을 뒤집으면 저절로 옳아진다
`slice(0, N)` 은 **정렬된 배열의 앞**을 남긴다.
- 현재(오름차순): 앞 = 가장 낮은 학년 → **출발선 후보가 버려짐**
- 뒤집은 뒤: 앞 = 목표에 가장 가까운 선수 → **경계 후보가 남음**

잘린 깊은 노드는 사라지지 않는다 — 가까운 선수를 전부 실패하면
그 각각에서 다음 라운드 선수가 다시 파생된다(`nextRoundQueue`). **버리는 게 아니라 미루는 것.**

상한(`PREREQ_FANOUT=6` · `DOWN_CONCEPT_CAP=20`)의 **역할이 바뀐다**:
"어떤 후보가 살아남느냐"(잘못) → **"진단이 얼마나 길어질 수 있느냐"**(안전장치, 유지).

## 7. 결과·학습경로 누수 (사용자 확정 ③④의 전제)

### 7-1. 발견된 결함
FE 가 종료 시 `finishDiagV3(true)` 를 부르면 `POST /v3/:id/finish` 를 **건너뛴다.**
그런데 그 안에만 있는 두 가지가 통째로 누락된다:
- `_applyDiagnosisV3NodeResults` → `user_node_status.diagnosis_result` 기록
- `buildRecommendedPath` → `learning_paths` 영속

**실측: 완료된 v3 세션 18건 중 `learning_paths` 가 있는 것은 2건.
`user_node_status` 13행 중 10행이 `diagnosis_result IS NULL`.**

→ 사용자 요구 ③("결과를 보여주고 학습경로로") 자체가 **지금은 성립하지 않는다.**

### 7-2. 조치
- 종료 경로가 **반드시 `/finish` 를 타도록** 통일. 또는
- `GET /v3/:id/result` 진입 시 completed 인데 반영 흔적이 없으면 **1회 지연 복구**
  (`getRecommendedPathBySession` 의 지연 빌드와 동일 패턴 — 일관성 확보)

### 7-3. "이어서 진단 →" 이 재개가 아니다 — ②의 전제
```html
<!-- learning-map.html — 라벨은 "이어서", 동작은 새 세션 생성 -->
<button onclick="startDiagnosisV3Unit('...')">이어서 진단 →</button>
```
`startDiagnosisV3Unit` 은 `POST /v3/start` 다.
**"나중에 이어서 하기"를 제공하려면 이 버튼이 실제로 재개해야 한다.**
진짜 재개 경로(`resumeDiagV3FromServer` + `/v3/active`)는 현재 인트로 배너에서만 접근 가능.
→ 단원 CTA 도 `/v3/active` 를 먼저 조회해 같은 단원 세션이 있으면 재개로 보낸다.
   (BE `getV3Units` 가 `lastSessionId` 를 반환하지 않아 FE 의 "결과 보기" 버튼도 죽어 있다 — 함께 수정)

| **INV-DV3-8** | **하위호환** — `downCount`·`prereqQueue`·`branchVerdicts` 가 없는 구 세션이 throw 없이 동작하고 조기종료를 타지 않는다 |

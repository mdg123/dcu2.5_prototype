# 다채움 플랫폼 일일 점검 시나리오 (자동 실행용)

> **버전**: 1.0 (2026-05-19 작성)
> **실행 주체**: 매일 09:30, `sonnet` 에이전트 1대가 본 문서를 단독으로 받아 0~5장을 순서대로 시뮬레이션하고, 결과를 `보고서/일일점검/YYYY-MM-DD_점검보고서.md` 로 저장한다.
> **자기완결성 원칙**: 본 문서를 받은 에이전트는 다른 작업지시서나 메모리 없이도 그대로 실행 가능해야 한다. 실행 중 의심나는 항목이 있어도 외부 문서를 추가로 읽지 말고, 본 문서의 "실측 방법" 그대로만 검증한 뒤 결과는 PASS/FAIL/SKIP/BLOCKED 중 하나로 기록한다.
> **시간 예산**: 1회 전체 실행 ≈ 75~90분 (시드 ≈ 5분, 16개 시나리오 ≈ 60~75분, 리포트 작성 ≈ 10분).

### 0.2 서버 기동

1. 기존 노드 프로세스가 떠 있는지 확인.
   ```powershell
   Get-Process node -ErrorAction SilentlyContinue
   ```
   이미 떠 있으면 `Stop-Process -Name node -Force` 로 정리한다(점검은 깨끗한 부팅에서 시작).
2. 의존성 설치(`node_modules`가 없거나 7일 이상 묵었을 때만):
   ```powershell
   npm install --no-audit --no-fund
   ```
3. 백그라운드로 서버 기동 (Bash 도구 `run_in_background: true`).
   ```bash
   cd "/mnt/c/Users/user/OneDrive - 금성초등학교/바탕 화면/다채움 품질 제고사업 프로토타입 - 실동작" && node server.js
   ```
   포트는 기본 **3000**. 다른 포트로 떠 있으면 즉시 P0 버그 등록.
4. 헬스체크(최대 30초 폴링):
   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/login.html
   ```
   `200`이 떨어질 때까지 5초 간격, 최대 6회. 실패 시 시나리오 전체를 BLOCKED로 종료하고 리포트.

### 0.5 PASS·FAIL 기준 (공통)

각 단계는 **(가) HTTP 2xx + (나) DB row 존재/필드값 일치 + (다) UI 표시 일치** 세 가지를 모두 만족할 때만 PASS. 하나라도 어긋나면 FAIL로 기록하고 다음 시나리오로 넘어간다(다음 시나리오에 영향이 큰 의존 실패는 SKIP 처리, BLOCKED 사유 명기).

### 0.6 측정 항목

- 각 API 호출의 응답 시간(ms). **느린 응답 임계값**: GET 1.5s, POST 2.5s 초과 시 P2 버그 등록.
- 콘솔 에러(`preview_console_logs`)에 `Uncaught` / `Error` 가 1건이라도 떨어지면 P1 등록.
- 네트워크 4xx/5xx 응답 중 의도된 권한 차단이 아닌 것은 즉시 P1 등록.

## 3. 시나리오 상세

### S01 — 인증·세션·역할별 GNB

**목적**: 회원가입/로그인/로그아웃/세션유지/역할별 메뉴 노출이 정상인지.

**계정**: `admin`, `teacher1`, `student1`, `parent1`, `staff1`

**선행조건**: 서버 기동 완료, 시드 보강 완료.

**단계별 액션**:
1. `preview_navigate /login.html` → 새 계정 `qa_temp_<타임스탬프>` / `1234` / `자동학생` / role=student 로 회원가입 (`preview_eval` 안 fetch).
2. 회원가입 직후 `GET /api/auth/me` 응답에 새 user.id 존재 확인.
3. 로그아웃 → `POST /api/auth/logout` → 다시 `/api/auth/me` 호출 시 401.
4. `admin`/`teacher1`/`student1`/`parent1`/`staff1` 5개 계정으로 순차 로그인 후 각각 `/`(포털) 페이지 진입 → GNB DOM 스냅샷.
5. `preview_eval` 로 `document.querySelectorAll('.gnb-menu a').length` 와 텍스트 추출.

**기대 결과**:
- 회원가입 응답 201, set-cookie 발급.
- 비밀번호 5자리(`12345`)는 400 + 한국어 메시지 "비밀번호는 숫자 4자리입니다."
- 역할별 GNB 메뉴 차이:
  - student: 포털/채움클래스/채움콘텐츠/스스로채움/채움성장/소통쪽지
  - teacher: 위 + 클래스 관리 진입 가능
  - admin: 위 + `/admin/` 진입 시 200, parent·staff는 `/admin` 진입 시 403 HTML
  - parent: 자녀(student1·student2)의 데이터 위젯 노출
  - staff: 일반 메뉴는 보이되 학생 전용·관리자 전용 액션 비활성/숨김

**실측 방법**:
- (API) signup/login/logout 응답 코드 + 본문
- (DB) `SELECT count(*) FROM users WHERE username LIKE 'qa_temp_%'` ≥ 1
- (UI) `/admin/` 직접 URL 입력 시 비-admin은 403 페이지 HTML(타이틀 "접근 권한이 없습니다") 노출 — 스크린샷 첨부

**추가 점검 — 세션 만료**: cookie의 maxAge가 7일인지 응답 헤더에서 확인(`Max-Age=604800`). 0 또는 누락 시 P1.

### S02 — 채움클래스 풀 사이클 (수업·과제·평가·알림장)

**목적**: 교사가 클래스를 만들고 학생 10명이 가입한 뒤, 게시물 4종을 발행 → 학생이 참여 → 교사 결과 확인까지.

**계정**: `teacher1`(개설자), `student1`~`student10`(멤버), `parent1`(자녀 진척 열람), `staff1`(권한 확인용)

**선행조건**: S01 완료, 10명 학생 시드 보강 완료.

**단계별 액션**:

1. **클래스 개설** (teacher1)
   - `POST /api/class` body: `{name:"일일점검 클래스 YYYYMMDD", class_type:"subject", grade:4, subject:"수학", is_public:true}` → 클래스 id, 6자리 가입 코드 회수.

2. **학생 10명 가입** (student1~10)
   - 각각 `POST /api/class/join` body: `{code:"<위 코드>"}` → 200.
   - parent1·staff1은 가입 시도해서 응답 코드만 기록(권한 정책 명시 없으면 결과만 기록).
   - `GET /api/class/:id/members` → members.length ≥ 11 (개설자+학생10).

3. **수업 게시(teacher1)**
   - `POST /api/lesson/:classId` body 예: `{title:"수업1: 분수 도입", description:"분수의 의미", lesson_date:"<오늘>"}`
   - 본문에 콘텐츠 1개 연결(S10에서 등록한 콘텐츠 또는 시드 콘텐츠 id 사용).
   - 학생 3명이 `lesson-player.html?lessonId=...` 진입 후 `POST /api/lesson/:classId/:lessonId/progress` 로 100% 이수 보고.

4. **과제 게시(teacher1)**
   - `POST /api/homework/:classId` body: `{title:"과제1: 분수 사진 찍기", description:"실생활 분수 1장", due_at:"<+3일>", allow_files:true}`
   - 학생 10명 모두 `POST /api/homework/:classId/:hwId/submit` 로 텍스트+선택파일 제출.
   - teacher1: 임의 학생 5명에게 점수 70~95 + 한 줄 피드백 채점.

5. **평가 게시(teacher1)**
   - `POST /api/exam/:classId` body: 4문항 객관식 questions JSON.
   - 학생 10명 응시: `start` → 답안 제출 → 자동채점.

6. **알림장 게시(teacher1)**
   - `POST /api/notice/:classId` body: `{title:"5/19 알림", content:"내일 우산 챙기기", require_confirm:true}` (한글은 preview_eval fetch).
   - 학생 10명 중 7명만 확인 처리(`POST /api/notice/:classId/:noticeId/read` 또는 `confirm`).

**기대 결과**:
- 클래스 코드는 영문/숫자 6자리 (정규식 `/^[A-Z0-9]{6}$/`).
- 멤버 11명, 수업 이수 3건, 과제 제출 10건/채점 5건, 평가 응시 10건(평균 점수 계산값 존재), 알림장 확인 7/10.
- parent1 로그인 후 자녀(student1) 클래스 진입 시 본인 자녀 데이터만 보임.

**실측 방법**:
- API 응답 + DB 직접 카운트:
  - `SELECT count(*) FROM class_members WHERE class_id=?` = 11
  - `SELECT count(*) FROM homework_submissions WHERE homework_id=?` = 10
  - `SELECT count(*) FROM exam_students WHERE exam_id=? AND status='submitted'` = 10
  - `SELECT count(*) FROM notice_reads WHERE notice_id=?` = 7
- UI: `/class/class-home.html?id=<id>` 진입해서 4개 탭 카운트 배지 스크린샷.

### S03 — 일반게시판·갤러리 게시판 글·댓글·좋아요·이미지·영상

**목적**: 학생이 일반게시판/갤러리 게시판에 텍스트 + 이미지 + (가능시) 영상 첨부 글을 올리고, 댓글·좋아요·미디어 렌더링까지.

**계정**: `teacher1`(개설자), `student1~3`

**선행조건**: S02 클래스 존재.

**단계별 액션**:
1. teacher1: 클래스에 `general` 카테고리 게시판 + `gallery` 카테고리 게시판이 보이는지 확인 (기본 시드 있음).
2. student1: `POST /api/board/:classId` body `{board_id:<general>, title:"오늘 점심 추천", content:"분식이 맛있었어요", category:"general"}` (한글은 preview_eval).
3. student2: 위 글에 댓글 2개 `POST /api/board/:classId/:postId/comments`.
4. student3: 위 글에 좋아요(있다면 `POST .../like`, 미구현이면 SKIP 표시).
5. student1: 갤러리 게시판에 **이미지 1장** + **mp4 영상 1개(또는 가짜 URL 1개)** 첨부 글 작성(`shareToGallery: true`).
   - 업로드: `POST /api/upload?type=board-image` → URL → 본문에 `<img src>` 또는 attachments에 추가.

## 4. 버그 리포트 마크다운 템플릿 (실행 에이전트 작성용)

발견한 버그마다 아래 블록을 하나씩 채워 `## 발견 버그` 섹션에 누적한다.

```markdown
### BUG-YYYYMMDD-NN  (예: BUG-20260519-01)

- **우선순위**: P0 Critical / P1 High / P2 Medium / P3 Low
- **시나리오**: S0X
- **모듈**: 채움클래스 / 채움콘텐츠 / 스스로채움 / 채움성장 / CBT / 관리자 / LRS / 인증 / 공통
- **제목**: (한 줄 요약, 30자 이내)
- **재현 단계**:
  1. 어떤 계정으로 어떤 URL 진입
  2. 어떤 입력
  3. 어떤 버튼 클릭
- **기대 결과**: …
- **실제 결과**: …
- **첨부**:
  - 스크린샷 경로: `보고서/일일점검/2026-05-19_attachments/bug-01.png`
  - HTTP 응답 발췌 (status + 본문 50~200자):
    ```json
    { "success": false, "message": "..." }
    ```
  - 콘솔 에러 로그:
    ```
    Uncaught TypeError: ...
    ```
- **추정 원인**: (예: routes/board.js L132 SQL JOIN 조건 누락)
- **영향 범위**: (어떤 사용자/모듈이 영향)
- **권장 처리**: (PM 또는 개발자가 다음에 봐야 할 파일 1~2개)
```

### 우선순위 가이드

- **P0 Critical**: 서버 다운, 로그인 불가, 데이터 손실, 다른 사용자 데이터 노출, XSS/SQLi.
- **P1 High**: 핵심 기능 동작 불가(과제 제출 실패, 시험 점수 누락, 가로 스크롤 발생, 가짜 영상 잔존, 401/403 부적절).
- **P2 Medium**: UX 불편(모달 크기 어긋남, 응답 지연 1.5s 초과, 라벨 누락, 한글 잘림).
- **P3 Low**: 사소한 디자인 어긋남(여백 4px 차이 등).

## 8. 자기 점검 — 본 문서가 자기완결적인지

본 문서 작성 시점 기준 가정:

- 서버는 `node server.js` 한 줄로 기동되며 별도 환경변수 필수 아님(SQLite 로컬 DB).
- 기본 시드 계정은 `db/schema.js` initSchema()가 항상 생성한다(`admin/0000`, `teacher1/1234`, `student1~3/1234`, `parent1/1234`, `staff1/1234`).
- 추가 학생(student4~10)은 본 문서 0.3절 절차로 매 실행마다 보강(이미 있으면 409 무시).
- 보고서 폴더는 본 문서 6장 절차로 생성한다.

위 가정에서 어긋난 경우(예: schema seedAdmin 비활성, 시드 사용자 정책 변경) 가장 먼저 `BLOCKED` 처리하고 PM에게 본 문서 갱신을 요청한다.
